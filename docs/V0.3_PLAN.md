## Part A. Fix the small-model replies (before the deadline)

### What the user saw on the phone (Qwen3 0.6B)

1. They asked "How many states are in Nigeria?". The model answered with an earlier reply: "Tomorrow is Wednesday, 21 October".
2. They asked again. The model recited a "memory": "the user is planning to write their PhD thesis… natural… without clinical language or pressure".
3. It then rambled: "perhaps they meant tomorrow is Wednesday… that makes sense, hence…".
4. It said Nigeria has 20 states. The correct answer is 36 states plus the Federal Capital Territory (Abuja).

### Root causes found in the code

| # | Cause | Where |
|---|---|---|
| A1 | Replies written by code (date and time answers, greetings) are saved in chat history. The last 6 messages are sent to the model, so the model copies "Tomorrow is Wednesday…". | `lib/orchestrator/orchestrator.ts` (`instant` reply, `history.slice(-CHAT_HISTORY_MESSAGES)`) |
| A2 | Memory pollution. The 0.6B model "extracts memories" from the conversation, and it copied the system prompt's own words ("do not use clinical language and do not add pressure") into a memory. Every question then gets that memory under "What you know about the user:", and the model repeats it. | `lib/orchestrator/memory-manager.ts`, `buildChatPrompt` in `prompt-builder.ts` |
| A3 | Sampling settings encourage loops. Chat uses `temperature: 0.3`. The Qwen3 model card says to use Temperature 0.7, TopP 0.8, TopK 20 and MinP 0 in non-thinking mode, and warns that greedy decoding "can lead to performance degradation and endless repetitions". It suggests `presence_penalty` 0–2 against loops. | `orchestrator.ts` generate options |
| A4 | Even with thinking turned off, the 0.6B model talks to itself ("perhaps they meant…"). Nothing cuts a reply that repeats its own sentences. | `orchestrator.ts` text path |
| A5 | A 0.6B model does not hold reliable facts. No prompt can fix this. | Model limit |

### Fixes (small, testable)

- **A1.** Mark code-written replies as local (a `local` flag on the message). Leave them, and the question that produced them, out of what the model sees. They stay visible on screen.
- **A2.**
  - Turn memory extraction off when the loaded model is under 1.5B.
  - Reject any extracted memory that shares a long phrase with the system prompt.
  - Inject memories only when the question is about the user ("my", "me", "remember", "what do you know about me").
  - Add Settings > Memory to view and delete memories.
  - Clear the existing polluted memories once, on upgrade.
- **A3.** For chat replies, use temperature 0.7, top_p 0.8, top_k 20 and a presence penalty of about 1.0. Check the exact llama.rn option names. Tool-JSON turns keep their low temperature.
- **A4.** After generation, keep the first 3 sentences. Cut the reply at the first sentence that repeats an earlier one.
- **A5.** Fix this honestly rather than with prompts:
  - Label 0.6B as "Quick helper: fast, can be wrong on facts".
  - Recommend Qwen3 1.7B on phones with 6 GB RAM or more.
  - When an online key is set (Part B), send factual questions online.
- **Tests.** Add the exact phone transcript to the real-model eval:
  - "what is tomorrow's date", then "how many states are in Nigeria" (asked twice);
  - no reply may copy an earlier reply or mention a memory.
  - Also add unit tests for A1, A2 and A4.

## Part B. Online AI with your own API key (optional)

**Goal:** the user can add an online key without losing the offline-first promise.

- **Where it lives:** Settings > AI > "Online model (optional)", with these fields:
  - Provider. "OpenAI-compatible" covers OpenAI, OpenRouter, Groq, Together, Google Gemini's OpenAI-compatible endpoint, and LM Studio or Ollama on the home network.
  - Base URL.
  - Model name.
  - API key.
  - A "Test connection" button.
- **When it is used** (a setting, default Off):
  - Off;
  - Only when I tap "Ask online";
  - For questions the phone model can't answer well;
  - Always for chat.
- **What never changes:** alarms, reminders, texts, calendar and tasks are still handled on the phone by the router and `directAction`. Only free-text chat goes online.
- **Privacy:**
  - The key is stored with `expo-secure-store`, like the Telegram token.
  - The key is never logged and never put in a URL.
  - Memories and documents are not sent unless a second toggle is on.
  - Replies answered online show an "Online" badge.
- **Reliability:** a 20-second timeout, then fall back to the phone model with a short notice.
- **Code shape:** add `lib/llm/remote-engine.ts`, returning the same `CompletionResult` as `llm-engine`. The orchestrator picks the engine. Use streaming if `expo/fetch` streams on Android; otherwise show the whole reply at once.
- **Cost:** the provider bills the user, and the screen says so.

## Part C. Beginora's own Telegram bot (no BotFather for users)

### Research findings
- **Deep links:** `https://t.me/<bot>?start=<code>` sends `/start <code>` to the bot. The code may use A–Z, a–z, 0–9, `_` and `-`, up to 64 characters ([Telegram bot features](https://core.telegram.org/bots/features)).
- **Bots can't write first:** a bot cannot message a person until that person has pressed Start.
- **Rate limits:** about 1 message per second per chat, and about 30 messages per second across the whole bot ([Telegram bot FAQ](https://core.telegram.org/bots/faq)).
- **One way to receive updates:** a bot can't long-poll (`getUpdates`) while a webhook is set. Each update is confirmed once, so many phones polling one bot would steal each other's messages.

### Why the bot token cannot go in the app
Anyone can pull a token out of an APK. With it, they could read every user's messages and send messages as Beginora. Also, as noted above, many phones polling one bot would steal each other's messages. A shared bot therefore needs a **small relay server**, which is the only part that holds the token.

### Design
1. **The bot.** The team creates @BeginoraBot (name to be checked) once with BotFather. Its token is stored only on the server.
2. **The relay.** A Cloudflare Worker (free tier) or a Supabase Edge Function, with a tiny database:
   - `link_codes(code, device_id, expires_at)`;
   - `links(device_id, device_secret_hash, chat_id)`;
   - `inbox(device_id, text, received_at)`, deleted after it is fetched or after 24 hours.
3. **Connecting** (one tap for the user):
   1. The user taps Settings > Connections > Telegram > **Connect**.
   2. The app calls `POST /link` with a random device ID. It gets back a one-time code (32 random characters, valid 10 minutes) and a device secret, which it stores in SecureStore.
   3. The app opens `t.me/BeginoraBot?start=<code>`. Telegram opens and the user taps **Start**.
   4. The webhook receives `/start <code>` and saves the chat ID against the device. The bot replies "Connected to Beginora."
   5. The app polls `GET /link/status` and shows Connected.

   The user never types a token or a chat ID.
4. **App to Telegram.** The app calls `POST /send` with the device secret, and the server calls `sendMessage`. Each device is limited (for example 20 messages an hour) to protect the bot-wide limit.
5. **Telegram to app (two-way).** The webhook stores incoming text in `inbox`. The existing `lib/telegram/telegram-runner.ts` fetches `GET /inbox` instead of `getUpdates`, during background runs or when the app opens.
6. **Disconnecting.** `/stop` in the bot, or Disconnect in the app, deletes the link and the inbox.
7. **Security:**
   - Verify Telegram's `X-Telegram-Bot-Api-Secret-Token` header on the webhook.
   - HTTPS only.
   - Hash device secrets.
   - Cap message length.
   - Do not log message text.
8. **Honest privacy wording:** Telegram and the relay can see these messages. Say so in the Connect screen, and label Telegram "uses the internet".
9. **Keep "Use my own bot"** under Advanced. The current code path still works for people who want no relay.

### What the user (project owner) must do
- Create the bot with BotFather.
- Create a Cloudflare (or Supabase) account.
- Set the token as a server secret.

These steps need the owner's own accounts, so the code cannot do them.

## Part D. UI redesign

### Sources combined
- **Apple Human Interface Guidelines:** clarity, deference, depth; 44 pt targets; Dynamic Type.
- **The ChatGPT ADHD blueprint:** remember for me, help me start, help me reset; one primary action per screen; no shame copy.
- **Univi (Dribbble), what to keep:** friendly look, emoji always with a word, clear empty state, mood dots on the calendar strip.
- **Univi, what to avoid:** a 15-emotion grid with duplicates, forced start and end times, "12:35AM – 13:35PM", lorem ipsum, hidden swipe actions, tiny tab labels.
- **NeuroRoutine screens, what to keep:** one page per step; "Optional" labels; 3 mood choices; serif large titles; light/dark switch.
- **NeuroRoutine, what to fix:** "8 left" countdowns, thumbs-down for "Upset", red for normal items, photo before the timer.

### Navigation
A floating glass tab bar with 4 tabs: **Today · Talk · Plan · Settings**.
- A raised **+ Capture** button sits on Today and Plan.
- The microphone stays in Talk.
- Labels are at least 11 pt with full contrast, and every tab has both an icon and a word.

### Screens
1. **Today:**
   - One-line greeting ("Good morning, Chi").
   - An **Up next** card for the next reminder or event, with Snooze and Done.
   - A **Your first step** card with a "Start 10 min" button.
   - Up to 3 tasks, then "See all".
   - Empty state: "Nothing urgent. You have some breathing room."
   - A gentle "2 steps done today". Never "8 left".
2. **Capture sheet:**
   - One field and a mic.
   - Parsed instantly by the existing router into chips ("Tomorrow · 09:00 · Edit"), then Save.
   - An unclear time gives 3 chips instead of a guess.
   - No time at all saves to **Inbox: sort later**.
3. **Step page** ("Help me start"):
   - Title and a duration that matches the list.
   - The **timer comes first**, then "Make it smaller".
   - Then an optional mood with 3 faces (calm, good, hard; no thumbs).
   - Then an optional note: "How did it go? A few words are enough."
   - A labelled **Done** button.
4. **Focus:** the timer only. At the end, offer Break / +10 min / Finish, with no criticism.
5. **Talk:**
   - The current chat.
   - A badge on each reply: "On phone" or "Online".
   - Suggestion chips: "Help me start…", "Remind me…", "What's next?".
6. **Plan:**
   - Today's timeline and a week view.
   - Flexible tasks are shown apart from fixed times.
   - Reminders are merged in (the existing `components/RemindersList.tsx`).
   - Edit and delete sit in a visible "…" menu, not hidden behind a swipe.
7. **Welcome back** (after 3+ days away): "Your tasks are still here." Options: See today / Review reminders / Clear old ones.
8. **Reset my day:** "Show what matters today", "Help me pick one thing", "Clear my list" (nothing is deleted without asking).
9. **Settings:**
   - AI: phone models, online model.
   - Connections: Telegram Connect, Calendar, Contacts and the others.
   - Notifications: sound, quiet hours, hide text on the lock screen.
   - Appearance: Light/Dark/System, text size, reduced motion.
   - Memory: view and delete.
   - Privacy.

### Design tokens
- **Keep:** the current light tokens in `lib/theme.ts`. They are already contrast-checked (accent `#467565` at 5.3:1, muted text at 4.7:1 or better).
- **Add:** a dark palette. Starting values: background `#202624`, surface `#2A332F`, text `#F0F2ED`, secondary text `#B9C3BD`, accent `#82B8A5`. Check every pair against 4.5:1 before shipping.
- **Times:** always use the device's 12/24-hour setting (`toLocaleTimeString`). Never mix the two formats.
- **Colour:** red only for real errors. Status is always colour plus a word or icon.

### Before coding the UI
Build a clickable HTML mockup of Today, Capture, Step page, Settings > AI and Telegram Connect, and review it on a phone. Then build the screens.
